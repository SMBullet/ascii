1. Sensitive Actions Performed Without an Authenticated Session

Description
The application does not validate the user session on the server before processing sensitive operations. The password change endpoint (POST /api/user/renewpassword) accepts and processes requests that contain no session cookie. Authorization relies only on the IPAEksperUserID and UserAccessToken parameters sent in the request body.

The application also issues a valid cookie on any request, including unauthenticated requests to non-existent resources (e.g. GET /nonexistant). The authenticated API endpoints then accept this cookie, so requests are never bound to an authenticated user session.

Consequences
An attacker who obtains a user's identifier and access token can perform sensitive operations, such as changing the account password, without authenticating. This leads to full account takeover.

2. Cookie Validation Bypass

Description
The application checks the integrity of the TS012a649e cookie and rejects requests where its value has been altered, returning a "Request Rejected" page. This check only applies when the cookie keeps its expected name. When the cookie was renamed, or replaced with an arbitrary name and an invalid value, the request was forwarded and processed successfully ("isSuccess": true).

Consequences
The cookie validation can be bypassed with very little effort. Requests that should be rejected reach the backend, which removes a layer of protection and makes it easier to exploit the other vulnerabilities in this report.

3. Multi-Factor Authentication Bypass

Description
The authentication endpoint (POST /api/user/login) returns the MFA state to the client in the twoFARequired and mfaSetupRequired parameters. Only the client side enforces these values; the server never validates them. Modifying the login response after submitting valid credentials made the following possible:

OTP verification bypass: Setting twoFARequired to false skips the one-time password step and gives full access to the application.
Mandatory MFA enrollment bypass: On provider accounts that have not yet enrolled, setting both twoFARequired and mfaSetupRequired to false skips the Google Authenticator setup and gives access to the provider modules (AXA Inventory, Invoicing, Fee Calculation).
Unauthorized MFA re-enrollment: On accounts with MFA already set up, setting mfaSetupRequired to true brings back the enrollment page. That page shows a new QR code and the TOTP secret key in clear text, which allows an additional authenticator device to be registered.
